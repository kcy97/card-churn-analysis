# 카드사 고객 이탈 위험군 식별

MySQL에 적재한 카드사 고객 10,127명 중, **아직 거래 중이지만 이탈 고객과 똑같이
행동하는 408명**을 골라내 개입 명단으로 만들고, 그 명단에 **1인당 연간 179달러까지**
쓸 수 있다는 예산 상한을 함께 산출한 프로젝트. CSV 적재부터 SQL 분석, 모델링,
대시보드와 주간 Slack 리포트까지 전 구간을 구성했다.

| | |
|---|---|
| 데이터 | [Kaggle — Credit Card customers](https://www.kaggle.com/datasets/sakshigoyal7/credit-card-customers) · 10,127명 × 21열 (유지 8,500 / 이탈 1,627) · 결측치 없음 |
| 스택 | MySQL 8.0 · Python 3.11 · XGBoost · SHAP · Streamlit |
| 모델 | 홀드아웃 2,026명 기준 ROC-AUC **0.993** · 이탈 Precision 0.90 / Recall 0.90 |
| 결과 | 개입 대상 **408명** · 1인당 연간 귀속 수익 **$179** (손익분기점) · 중간 시나리오 연 **$18,305** |

> 이 저장소의 숫자는 전부 `card_analysis.ipynb` 를 끝까지 실행해 나온 값이다.
> 노트북 출력과 README가 어긋나면 노트북이 맞다.

## 0. 이 모델이 할 수 있는 것과 없는 것

`Attrition_Flag` 를 라벨로 쓴 지도학습 이진 분류이므로 **이탈 예측 모델**이다.
다만 데이터가 고객 1인당 1행으로 요약된 스냅샷이고 관측 기간과 예측 기간이
분리되지 않아 **이탈 시점과 리드타임은 예측하지 못한다.**

더 중요한 제약이 하나 있다. 이탈 고객의 낮은 거래량은 이탈의 *원인*이 아니라
이미 이탈이 진행된 *결과*일 수 있다. 즉 모델이 학습한 신호의 일부가 선행지표가
아닐 가능성이 있다. 그래서 산출물은 '이탈 예정자 명단'이 아니라
**접촉 우선순위 명단**으로 쓴다.

---

## 1. 이탈은 *누가* 가 아니라 *어떻게 쓰는가* 가 결정한다

성별·소득·결혼여부 등 인구통계 축은 세그먼트 간 이탈률 편차가 2~4%p에 그친다.
행동 변수는 다르다.

| 지표 | 유지 고객 | 이탈 고객 | 격차 |
|---|---|---|---|
| 총 거래건수 | 68.7건 | 44.9건 | **−34.6%** |
| 총 거래금액 | $4,655 | $3,095 | **−33.5%** |
| 거래건수 변화율 (Q4/Q1) | 0.74 | 0.55 | **−25.3%** |
| 고객센터 연락 횟수 | 2.36회 | 2.97회 | **+26.1%** |
| 나이 | 46.3세 | 46.7세 | +0.9% |

---

## 2. 다만 "거래가 적을수록 이탈"은 단조 관계가 아니다

SHAP 중요도 1위가 거래건수라 "적을수록 위험"으로 읽기 쉽다. **중요도는 방향을
말하지 않으므로** 십분위로 끊어 실제 이탈률을 직접 확인했다.

| 십분위 | 거래건수 | 고객수 | 이탈률 |
|---|---|---|---|
| 1 | 10~33건 | 1,018 | 26.6% |
| 2 | 34~41건 | 1,058 | 38.5% |
| **3** | **42~50건** | 1,052 | **48.4%** ← 정점 |
| 4 | 51~61건 | 1,037 | 20.9% |
| 5 | 62~67건 | 958 | 8.1% |
| 10 | 93~139건 | 988 | 0.1% |

**가장 적게 쓰는 층이 가장 위험하지 않다.** 거래가 아주 적은 고객은 애초에 카드를
쓰지 않는 사람들이라 떠날 관계 자체가 없다. 위험한 쪽은 **쓰던 사람이 줄어든**
경우다. 임계값을 직관으로 잡지 않고 분포로 확인한 이유다.

---

## 3. 임계값은 각 변수의 사분위 경계에서 잡았다

| 조건 | 임계값 | 근거 (해당 변수의 사분위) | 이탈군 평균 |
|---|---|---|---|
| `Total_Trans_Ct` | < 45건 | 하위 25% 경계 = 45.0 | 44.9건 |
| `Total_Ct_Chng_Q4_Q1` | < 0.6 | 하위 25% 경계 = 0.58 | 0.55 |
| `Contacts_Count_12_mon` | ≥ 3회 | 상위 25% 경계 = 3.0 | 2.97회 |
| `Total_Relationship_Count` | ≤ 3개 | 하위 25% 경계 = 3.0 | 3.28개 |

사분위 경계와 이탈군 평균이 같은 방향이라 두 근거가 일치한다.

---

## 4. 룰 기준선을 먼저 세우고, 모델은 그보다 나은 만큼만 채택했다

모델을 정당화하려면 **모델 없이 되는 것**보다 나아야 한다. 위 네 조건을
SQL `CASE` 로 세기만 한 룰 스코어카드(`v_rule_scorecard`)를 기준선으로 삼았다.

| 걸린 신호 | 고객수 | 이탈 고객수 | 이탈률 | 리프트 | 포착률 |
|---|---|---|---|---|---|
| 0개 | 1,691 | 44 | 2.6% | 0.16 | 2.7% |
| 1개 | 4,039 | 284 | 7.0% | 0.44 | 17.5% |
| 2개 | 2,865 | 491 | 17.1% | 1.07 | 30.2% |
| 3개 | 1,147 | 497 | 43.3% | 2.70 | 30.5% |
| **4개** | **385** | 311 | **80.8%** | **5.03** | 19.1% |

그 다음 모델과 나란히 놓았다 (`v_rule_vs_model`).

| 방식 | 대상 고객수 | 대상군 이탈률 | 전체 이탈자 포착률 |
|---|---|---|---|
| 룰 (신호 4개) | 385명 | 80.8% | 19.1% |
| 모델 (매우높음) | 2,026명 | 79.9% | **99.4%** |

**정밀도는 사실상 같다.** 모델을 채택한 근거는 정확도가 아니라 포착률이다 —
룰은 이탈 고객의 19.1%만 잡지만, 모델은 같은 정밀도를 유지하면서 99.4%를 넣는다.

여기서 하나 더 보인다. **신호 2~3개 구간이 전체 이탈자의 61%를 담고 있다.**
룰만으로 운영하면 정밀한 대신 대상이 너무 좁다는 뜻이고, 이것이 모델을 쓰는
실질적 이유다.

> 룰 쪽 수치는 SQL 집계만으로 나오므로 모델이 바뀌어도 재현된다.
> 모델 쪽 포착률은 아래 5절의 한계(in-sample)를 안고 있는 값이다.

## 5. 등급은 확률의 5분위로 끊는다

고정 임계값(예: 확률 0.8 이상)이 아니라 **분위**로 끊었다. 각 등급 인원이 거의
같아 "상위 20%에 접촉한다" 식의 **인원 기준 예산 설계**가 가능하기 때문이다.
고정 임계값은 재학습할 때마다 대상 인원이 요동쳐 예산 계획이 어렵다.

| 등급 | 고객수 | 실제 이탈률 | 확률 구간 |
|---|---|---|---|
| 매우낮음 | 2,026 | 0.0% (0명) | 0.0000 ~ 0.0003 |
| 낮음 | 2,025 | 0.0% (0명) | 0.0003 ~ 0.0009 |
| 보통 | 2,025 | 0.0% (0명) | 0.0009 ~ 0.0034 |
| 높음 | 2,025 | 0.4% (9명) | 0.0034 ~ 0.0922 |
| 매우높음 | 2,026 | **79.9%** (1,618명) | 0.0927 ~ 0.9999 |

**실제 이탈률이 등급 순서대로 단조 증가하는지가 이 스코어의 검증 지표**이고,
이 값은 대시보드에 항상 띄워 둔다. 단조성이 깨지면 재학습 신호로 본다.

**개입 대상**은 매우높음 등급 중 아직 거래 중인 **408명**이다.

> **한계:** 위 등급은 학습 데이터를 포함한 in-sample 스코어링이라 등급별 이탈률이
> 낙관적으로 나온다. 편향 없는 값을 보려면 각 고객을 자기 데이터가 학습에
> 들어가지 않은 모델로만 채점해야 한다(out-of-fold). 후속 과제.

## 6. 성과는 거래액이 아니라 카드사 귀속 수익으로 말한다

`Total_Trans_Amt` 는 고객이 카드로 결제한 총액이고, 그 돈은 가맹점으로 간다.
카드사에 남는 건 거래액에서 떼는 **가맹점 수수료**와 리볼빙 잔액에 붙는 **이자**다.
거래액에 더해지는 값이 아니라 잘라낸 몫이므로 두 열을 합산하지 않는다.

개입 대상 408명 — 연간 평균 거래금액 $2,594, 평균 리볼빙 잔액 $937.

| 시나리오 | 방어 고객 | 보존 거래액 | 가맹점 수수료 | 리볼빙 이자 | **귀속 수익** |
|---|---|---|---|---|---|
| 보수적 20% | 81명 | $210,133 | $3,152 | $11,384 | **$14,536** |
| 중간 25% | 102명 | $264,612 | $3,969 | $14,336 | **$18,305** |
| 낙관적 30% | 122명 | $316,497 | $4,747 | $17,147 | **$21,894** |

**1인당으로 보면 수수료 $39 + 리볼빙 이자 $141 = $179.**
이 값이 개입 단가의 손익분기점이다. 가정은 전부 `economics.py` 한 파일에 있다.

**수익의 79%가 리볼빙 이자에서 나온다.** 즉 이 금액은 수수료율이 아니라
**APR 가정이 좌우한다.** APR 20%로 보면 1인당 $226이 된다.

### 평균을 어느 집단에서 뽑는지가 결과를 바꾼다

최상위 등급 **전체**(2,026명)의 평균 거래액은 $2,993이지만, 여기에는 **이미 떠난
1,618명**의 거래액이 섞여 있다. 막으려는 대상의 가치는 **아직 거래 중인 408명의
$2,594**로 계산해야 한다. 전자를 쓰면 보존 규모가 15% 부풀려진다.

### 이 코호트는 고가치 고객이 아니다

| 구분 | 평균 거래액 | 평균 리볼빙 잔액 |
|---|---|---|
| **고위험 유지군 (개입 대상)** | **$2,594** | **$937** |
| 전체 평균 | $4,404 | $1,163 |
| 안전군 (매우낮음 등급) | $4,595 | $1,396 |

거래액이 전체 평균의 59% 수준이다. 따라서 이 캠페인의 논리는
"가치 높은 고객을 지킨다"가 아니라 **"이탈 확률이 높은 구간을 손익분기점 안에서
싸게 방어한다"** 가 된다. 고단가 프리미엄 혜택으로는 수익이 남지 않는다.

## 한계

- **시점과 리드타임을 예측하지 못한다.** 스냅샷 데이터라 "언제 이탈할지"를 잴 수
  없고, 낮은 거래량이 이탈의 원인이 아니라 결과일 수도 있다. 408명은 이탈이
  확정된 집단이 아니다.
- **대손을 반영하지 못한다 — 이탈이 오히려 이득인 고객을 구분할 수 없다.**
  리볼빙 이자를 수익으로만 잡았지만, 회수되지 않으면 대손상각 대상이고 원금까지
  손실이다. 한도까지 쓰고 리볼빙으로 버티다 연체로 가는 고객이라면 그 이탈은
  오히려 손실 차단이다. 연체 이력·신용등급·대손상각 여부가 데이터에 없어
  이자를 꾸준히 내주는 우량 고객과 구분되지 않는다.
- **자발적 해지와 직권 해지가 구분되지 않는다.** `Attrition_Flag` 는 이탈을 한
  종류로만 표기한다. 스스로 떠난 고객과 연체로 끊긴 고객이 섞여 있을 수 있고,
  두 집단은 행동 패턴이 비슷해 보이지만 대응은 정반대여야 한다.
- **리볼빙 잔액의 방향을 해석하지 못했다.** `Total_Revolving_Bal` 은 SHAP 중요도
  3위인데 이탈과의 단순 상관은 −0.02로 거의 0이다. 비선형이나 상호작용으로
  작동하고 있다는 뜻이고, 방향을 설명하지 못한 채 남겨 두었다.
- **이자 추정은 상한에 가깝다.** 잔액이 평균 일일 잔액이 아닌 스냅샷이고,
  개입 대상의 **42%는 리볼빙 잔액이 0원**이라 이자는 나머지 58%에서만 나온다.
- **손익분기점 $179는 아직 검증되지 않았다.** 방어 성공률 20~30%는 캠페인 실적이
  없어 시나리오로 둔 값이다. 실제 데이터가 쌓이면 이 숫자부터 교체해야 한다.
- **운영 리스크** — 개입안이 "추가 상품 가입 유도"인데, 대손 위험이 높은 고객에게
  한도와 상품을 늘려 주면 부실을 키운다. 집행 전 신용 리스크 필터가 선행돼야 한다.
- **인코딩 맵이 없으면 추론이 깨진다.** 범주형을 `LabelEncoder` 로 변환하는데
  매핑을 저장하지 않으면 신규 고객 스코어링 시 같은 인코딩이 보장되지 않는다.
  `label_maps.json` 으로 함께 저장하도록 수정했다.

## 실행

```bash
git clone https://github.com/kcy97/card-churn-analysis.git
cd card-churn-analysis
mkdir -p data                 # Kaggle에서 BankChurners.csv 를 받아 data/ 에 저장

cp .env.example .env          # MYSQL_* 및 CSV_PATH 입력
pip install -r requirements.txt

docker compose up -d          # MySQL 8.0
python db_setup.py            # 스키마 → 적재 → 검증 → 뷰

jupyter notebook notebooks/card_analysis.ipynb
streamlit run app.py
python weekly_report.py --test
```

`.env` 의 `CSV_PATH` 는 **프로젝트 루트 기준 상대경로**(`data/BankChurners.csv`)로
적는다. 노트북이 `notebooks/` 안에 있어 작업 폴더가 루트가 아니므로, 코드에서
`.env` 의 위치를 루트로 잡아 경로를 해석한다.

`db_setup.py` 는 적재 후 행 수 10,127 / 유지 8,500 / 이탈 1,627 / CLIENTNUM 중복 0 을
검증하고, 하나라도 어긋나면 중단한다.

MySQL 없이 SQL만 확인하려면 `python run_analysis.py --engine sqlite` —
CSV로 로컬 SQLite DB를 만들어 `sql/03_eda.sql` 을 그대로 실행한다.

| 파일 | 설명 |
|------|------|
| `notebooks/card_analysis.ipynb` | 전체 분석 (적재·정합성 → EDA → 십분위·사분위 점검 → 룰 기준선 → 모델 → 등급 → 수익 환산) |

| `sql/03_eda.sql` | EDA 쿼리 7종 (CTE · `NTILE` 십분위 · 조건부 집계 · 신호 스코어카드) |
